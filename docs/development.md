# Development Guide for LLM Coding Agents

**Purpose**: This teaches you HOW to set up, run, build, and debug this project with the exact commands and conventions used here.

**Read this first**:
- `docs/architecture.md` for file placement rules.
- `docs/testing.md` for test patterns and Playwright debugging.
- `docs/meta/styleguide.md` for mandatory engineering + WebGL2 shader rules.

## Setup (One-time)

```bash
# Install dependencies (npm is the expected package manager)
npm install

# Build WASM module (required for full functionality)
npm run wasm:build

# Install Playwright browsers (for E2E tests)
npx playwright install chromium
```

### Prerequisites

- **Node.js**: v18+ (v20 LTS recommended)
- **npm**: v9+ (comes with Node.js)
- **Rust + wasm-pack**: Required for WASM module
  ```bash
  # Install Rust
  curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
  
  # Install wasm-pack
  cargo install wasm-pack
  ```

## Run Locally (Dev Server)

```bash
# Starts Vite dev server on port 3000
npm run dev
```

- Dev URL: `http://localhost:3000`
- Port is fixed by the script (`vite --port 3000`). If you must change it, pass a different port:

```bash
npm run dev -- --port 3001
```

### Dev Server Features

- **Hot Module Replacement (HMR)**: Changes auto-reload
- **CORS headers**: Configured for SharedArrayBuffer support
- **Auto-open**: Browser opens automatically

## WASM Module

The project includes a Rust-based WASM module for performance-critical geometry calculations.

### WASM File Structure

```
src/wasm/mdimension_core/
├── Cargo.toml           # Rust dependencies
├── src/
│   └── lib.rs           # Rust source code
└── pkg/                 # Generated by wasm-pack (do not edit)
    ├── mdimension_core.js
    ├── mdimension_core.d.ts
    └── mdimension_core_bg.wasm
```

### Building WASM

```bash
# Build the WASM module
npm run wasm:build

# Or directly:
wasm-pack build ./src/wasm/mdimension_core --target web
```

### Using WASM in TypeScript

```typescript
import init, { some_function } from 'mdimension-core'

// Initialize WASM (typically in app startup)
await init()

// Use WASM functions
const result = some_function(input)
```

### WASM Aliasing

- **Production**: `mdimension-core` → `./src/wasm/mdimension_core/pkg`
- **Testing**: `mdimension-core` → `./src/tests/__mocks__/mdimension-core.ts`

## Standard Workflow (What to do when changing code)

### Before you start (fast sanity)

```bash
npm test
```

### While developing

- Keep `npm run dev` running for manual iteration.
- When debugging runtime issues, prefer **Playwright + console logs** (see `docs/testing.md`).

### Before you claim work is done (required)

```bash
npm test
npm run lint
npm run build
```

### Full verification checklist

1. `npm test` — all unit/component tests pass
2. `npm run lint` — no linting errors
3. `npx playwright test` — E2E tests pass
4. `npm run build` — production build succeeds
5. `npm run preview` — manual verification in production mode

## Decision Tree: "What command should I run?"

- If you changed TypeScript/React logic and want confidence → `npm test`
- If you changed rendering/shaders and need WebGL validation → `npx playwright test`
- If you changed dependencies, config, or build pipeline → `npm run build`
- If you touched formatting/style → `npm run lint` and `npm run format`
- If you changed WASM/Rust code → `npm run wasm:build` then `npm test`

## Debugging Rules (Project-specific)

### CRITICAL: No fetch-based debugging

- **Never use fetch-based debugging**. Do not add "reporting endpoints" or send logs over HTTP.
- This is a strict requirement — fetch debugging causes resource exhaustion.

### Correct debugging approach

For runtime bugs:
1. Add `console.log` (temporarily) in the browser code.
2. Capture and assert logs via Playwright (`page.on('console', ...)`).
3. Remove noisy logs after resolving.

### Playwright debugging template

```ts
import { test } from '@playwright/test'

test('Debug specific behavior', async ({ page }) => {
  const logs: string[] = []

  page.on('console', (msg) => {
    logs.push(`[${msg.type()}] ${msg.text()}`)
  })

  await page.goto('/')
  await page.waitForTimeout(3000)

  // Print all captured logs
  console.log('=== Captured Logs ===')
  logs.forEach(log => console.log(log))
})
```

### Shader debugging

For shader issues:
1. Use Playwright with WebGL shader compile guard
2. Check for compile/link errors in console
3. Add debug outputs via color channels (temporary)

```glsl
// Debug: visualize a value as color
fragColor = vec4(vec3(debugValue), 1.0);
```

## Troubleshooting

### Dev server won't start

- Check if port 3000 is already in use:
  ```bash
  lsof -i :3000
  ```
- Try a different port:
  ```bash
  npm run dev -- --port 3001
  ```

### Tests hang or the system gets sluggish

- Stop running node processes:
  ```bash
  killall -9 node
  ```
- Clean up Vitest workers:
  ```bash
  node scripts/cleanup-vitest.mjs
  ```
- Re-run a single test file to isolate:
  ```bash
  npx vitest run src/tests/path/to/test.test.ts
  ```

### Playwright fails to launch the app

- Playwright expects `http://localhost:3000` and auto-starts the dev server via `playwright.config.ts`.
- If you already have a server running, Playwright will reuse it (local mode).
- Check that the dev server is running:
  ```bash
  curl http://localhost:3000
  ```

### WASM module not found

- Rebuild WASM:
  ```bash
  npm run wasm:build
  ```
- Check that `src/wasm/mdimension_core/pkg/` exists.

### Canvas is black / no render

- Check browser console for WebGL errors
- Run Playwright test to capture errors:
  ```bash
  npx playwright test scripts/playwright/object-types-rendering.spec.ts
  ```
- Verify shader compilation succeeded

### WebGL context lost

- Reduce quality settings
- Close other GPU-intensive applications
- Check for driver issues

### TypeScript errors after dependency update

- Clear cache and rebuild:
  ```bash
  rm -rf node_modules/.vite
  npm run build
  ```

### ESLint errors

- Auto-fix what's possible:
  ```bash
  npm run lint -- --fix
  ```

### Three.js "Multiple instances" warning

- This is expected in tests and suppressed by setup.ts
- In production, ensure only one Three.js import

### Memory issues during tests

- Never increase `maxWorkers` in vitest.config.ts
- Keep tests small and isolated
- Clear large arrays between test iterations

## Common Mistakes

❌ **Don't**: Run `vitest` watch mode in automation or scripts.
✅ **Do**: Use `npm test` (`vitest run`) for CI-safe runs.

❌ **Don't**: Debug with fetch calls, remote log collectors, or "debug endpoints".
✅ **Do**: Use Playwright and inspect/capture console logs.

❌ **Don't**: Put scripts, scratch docs, or screenshots in the repo root.
✅ **Do**: Use `scripts/tools/`, `docs/`, and `screenshots/`.

❌ **Don't**: Add raw HTML controls or a new UI library.
✅ **Do**: Use/extend `src/components/ui` primitives.

❌ **Don't**: Skip `npm run build` after pipeline-level changes.
✅ **Do**: Always run `npm run build` before claiming the change is complete.

❌ **Don't**: Commit without running tests.
✅ **Do**: Always run `npm test && npm run lint` before committing.

❌ **Don't**: Modify `vitest.config.ts` memory settings.
✅ **Do**: Keep `maxWorkers: 4` and `pool: 'threads'` stable.

❌ **Don't**: Use console.log for persistent debugging.
✅ **Do**: Use Playwright console capture for debugging, remove logs after.
